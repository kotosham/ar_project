# Консоль оператора — инструкция

Пошаговое руководство для человека, который запускает стек: в симуляции и на реальном роботе.
Документ не заменяет [`RUNBOOK.md`](RUNBOOK.md) (подробная эксплуатация по терминалам),
[`HIL_BRINGUP_CHECKLIST.md`](HIL_BRINGUP_CHECKLIST.md) (обязательные проверки безопасности на
железе), [`architecture/MODES.md`](architecture/MODES.md) (чем `flat` отличается от `vlm`) и
[`HOUSE_BENCHMARK.md`](HOUSE_BENCHMARK.md) (сценарии домашнего бенчмарка). Он объясняет, что
делать руками и в каком порядке.

---

## 1. Что это и чего оно НЕ делает

Консоль — это веб-страница на `http://127.0.0.1:8090`, которая:

* выбирает режим (симуляция / реальный робот) и планировщик (`vlm` / `flat` / `mock`);
* показывает мир и его превью, если режим — симуляция;
* принимает токен и модель VLM и записывает их в `vlm.env`;
* показывает **преflight-проверки**: что уже работает, что молчит, и почему нельзя стартовать;
* в режиме симуляции запускает и останавливает стек;
* отправляет задание и показывает встроенный монитор миссии (тот же дашборд, что на порту 8088).

Чего она **не** делает:

* **не управляет роботом напрямую** — рулит executive на Pi, консоль лишь отправляет задание и
  операторский `Стоп`;
* **не поднимает робота за вас** — на железе Pi и edge поднимаются руками, в терминалах;
  консоль их только *видит*. В режиме железа кнопка «Запустить стек» намеренно недоступна;
* **не подсказывает решения планировщику** — она не фильтрует и не переписывает то, что вернула
  модель. Единственное вмешательство оператора — `Стоп`, и это abort, а не подсказка;
* **не хранит историю** — журнал стека и лента событий миссии живут в оперативной памяти
  процесса (см. §7);
* **не имеет аутентификации по умолчанию** — порты 8090 и 8088 публикуются только на
  `127.0.0.1`. Для доступа с другой машины пробрасывайте порт:
  `ssh -L 8090:127.0.0.1:8090 user@host`. Наружу не выставлять.

Три слоя, которые консоль сводит вместе:

```
  operator_console   консоль оператора (ваш ПК, docker)   -- порт 8090
  edge_layer         "мозг": SLAM, детектор, оркестратор  -- edge-бокс или тот же ПК
  mission_bringup    "робот": Gazebo ЛИБО Pi + RealSense + CAN
```

Верхний слой в обоих режимах **один и тот же**. Нижний — принципиально разный. Подробнее об
этом честно написано в §7.

## 2. Быстрый старт в симуляции — одна команда

Нужен только Docker (Docker Desktop на Windows и macOS, `docker-ce` на Linux).

| ОС | Команда |
|---|---|
| Linux | `cd ar_project && ./run.sh up` |
| macOS | `cd ar_project && ./run.sh up` |
| Windows (PowerShell) | `cd ar_project; .\run.ps1 up` |

Затем откройте **http://127.0.0.1:8090**.

Что произойдёт при первом запуске:

1. скрипт создаст `docker/.env` из `docker/.env.example`;
2. скрипт создаст `object_tracking/planner_orchestrator/vlm.env` из `vlm.env.example` с правами
   `0600`;
3. если NVIDIA не найдена, сборка edge пойдёт под CPU, и скрипт об этом скажет;
4. поднимется контейнер `console`, и скрипт напечатает адрес.

> **Не запускайте `docker compose` руками в обход `run.sh`/`run.ps1` при первом старте.**
> `vlm.env` подключается bind-mount-ом. Если файла нет, Docker создаст на его месте **каталог**,
> `env_file` молча не подхватится, а консоль не сможет записать туда токен. Симптом: «токен
> сохранён», но `token_set` остаётся `false`. Лечится удалением каталога и повторным `./run.sh up`.

Дальше — мастер из шести шагов на самой странице: Режим → Планировщик → VLM → Мир →
Подключение → Работа. Шаг «Мир» доступен только в симуляции.
Кнопка «Запустить стек» появляется только в режиме симуляции: там консоль владеет процессом
`ros2 launch` и может его перезапустить.

## 3. Быстрый старт с реальным роботом — пять шагов

**Всего пять шагов: два на роботе и edge для транспорта, два для подъёма стека, один на вашем ПК.**
Порядок обязателен: сначала транспорт, потом Pi, потом edge, потом консоль.

Перед первым запуском на железе пройдите раздел **B** из
[`HIL_BRINGUP_CHECKLIST.md`](HIL_BRINGUP_CHECKLIST.md) (безопасность моторов, колёса над землёй).
Ни один пункт ниже его не заменяет.

### Шаг 1 — на edge-боксе: транспорт и время

```bash
cd ~/ros2_ws/src/ar_project/deploy/transport
bash install_transport.sh edge            # адрес определится сам
# либо явно:  bash install_transport.sh edge 192.168.1.10
```

Что физически делает человек: заходит по ssh на GPU-машину и запускает одну команду с `sudo`.

Что видно на экране: шесть шагов `[1/6]`…`[6/6]`, затем `OK: служба rmw-zenoh-router активна`,
`OK: порт 7447 слушается`, чек-лист и напечатанная преамбула терминала. Если роутер не поднялся,
скрипт скажет об этом и даст команду `journalctl -u rmw-zenoh-router -f`.

Запомните адрес edge — он нужен на шагах 2 и 5. Проверить, что скрипт всё подставил:

```bash
grep -n 'tcp/' /etc/zenoh/zenoh_session_config.json5     # должен быть ваш IP, а не EDGE_HOST
```

### Шаг 2 — на Raspberry Pi: транспорт, время, CAN

```bash
cd ~/ros2_ws/src/ar_project/deploy/transport
bash install_transport.sh pi 192.168.1.10        # адрес edge из шага 1
```

Что видно на экране: те же шесть шагов, потом вывод `check_offset.sh` (сразу после рестарта
chrony `FAIL` — нормально, повторите через минуту, нужен `PASS` с offset и RMS ≤ 0.02 с), потом
проверка `can0` и проверка доступности роутера.

Если `can0` опущен, скрипт **сам его не поднимает** — это изменение состояния железа. Он печатает
точную команду; выполните её, убедившись, что колёса на стенде:

```bash
sudo ip link set can0 up type can bitrate 1000000
```

Если скрипт написал «Роутер недоступен» — вернитесь на шаг 1, стек дальше не пойдёт.

### Шаг 3 — на Pi: поднять робота (одна команда)

Сначала вставьте преамбулу (её же печатает `install_transport.sh`):

```bash
cd ~/ros2_ws
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
unset ROS_LOCALHOST_ONLY ROS_STATIC_PEERS ROS_AUTOMATIC_DISCOVERY_RANGE ROS_DISCOVERY_SERVER FASTDDS_BUILTIN_TRANSPORTS FASTRTPS_DEFAULT_PROFILES_FILE
export ROS_DISABLE_ROS2CLI_DAEMON=1
source ~/ros2_ws/src/ar_project/deploy/transport/transport_env.sh
```

`unset` шести переменных обязателен: остатки настроек Fast DDS перебивают zenoh, и узлы
перестают находить друг друга. Именно поэтому этот блок повторяется девять раз в [`RUNBOOK.md`](RUNBOOK.md) —
единый launch сокращает число терминалов, но не отменяет преамбулу: её нужно выполнить
в том терминале, из которого запускается launch.

**Одна команда** — единый launch воспроизводит последовательность `RUNBOOK.md` §2.1 внутри
одного файла (hardware_bringup → RealSense → map_odom_relay → Nav2 → executive), разнося
ступени таймерами:

```bash
ros2 launch ar_project mission_bringup.launch.py mode:=hardware layer:=robot
```

Что видно на экране: выход lely-мастера в `Operation Enabled` на обоих приводах, затем поток
кадров RealSense, затем активация lifecycle-узлов Nav2.

> **Задержки между ступенями не измерены на стенде.** `delay_realsense_s:=3`,
> `delay_map_relay_s:=5`, `delay_nav2_s:=8`, `delay_executive_s:=14` получены пересчётом
> из симуляции, а не замером времени подъёма `ros2_control` по CAN и инициализации RealSense.
> Если Nav2 стартует раньше, чем появился `map->odom`, увеличьте задержки аргументами:
> `... delay_nav2_s:=14 delay_executive_s:=20`. Ручная последовательность из пяти терминалов
> (`RUNBOOK.md` §2.1) остаётся рабочим запасным вариантом и от неё ничего не отнято.

### Шаг 4 — на edge: поднять «мозг» (одна команда)

Та же преамбула. `edge_layer` включает `edge_bringup` (реле камеры, RTAB-Map, коррекция
`map->odom`, дашборд) и поднимает детектор с оркестратором на `/camera_edge/*`:

```bash
ros2 launch ar_project mission_bringup.launch.py mode:=hardware layer:=edge \
  planner:=vlm venv_python:=$HOME/.venvs/ros-jazzy-ml/bin/python
```

Креды VLM берутся из окружения. Либо подгрузите `vlm.env` заранее, либо укажите файл явно:

```bash
set -a; source ~/ros2_ws/src/object_tracking/planner_orchestrator/vlm.env; set +a
# либо:  ... vlm_env_file:=~/ros2_ws/src/object_tracking/planner_orchestrator/vlm.env
```

Значение ключа нигде не печатается: launch пишет в журнал только адрес API, модель и
`токен: задан / НЕ задан`. Если `planner:=vlm`, а адрес пуст, в журнале появится громкое
предупреждение — иначе `vlm_client.make_client` молча уходит в mock-планировщик и прогон
оказывается не тем, что вы думаете.

Ручной вариант в три терминала (`RUNBOOK.md` §2.1, Edge T1–T3) продолжает работать.

**Сразу после Edge T1 — и только после него** — вернитесь на Pi и включите сжатие камеры:

```bash
bash ~/ros2_ws/src/ar_project/deploy/tune_camera_compression.sh
```

Раньше эту команду выполнить нельзя: параметры `compressedDepth.*` объявляются лениво, только
когда на топик подпишется потребитель, то есть edge-реле (`RUNBOOK.md`:152-153). Запущенная до
шага 4 она честно напишет «no compressedDepth.format param found» и ничего не сделает.

### Шаг 5 — на вашем ПК: консоль

```bash
EDGE_HOST=192.168.1.10 ./run.sh robot        # Windows: .\run.ps1 robot 192.168.1.10
```

Откройте **http://127.0.0.1:8090**, выберите режим «Реальный робот».

Что видно на экране: сначала блок «Ожидаю подключения робота…» с пульсирующей точкой и списком
ключевых потоков с их возрастом. По мере подъёма робота потоки один за другим зеленеют. Блок
меняется на зелёное «ПОДКЛЮЧЕНО» **только когда все ключевые потоки свежие** —
`/robot_health`, `/scan`, `/odometry/filtered`, `/joint_states`, `/camera_edge/color/camera_info`.
Именно свежие, а не «видны в графе»: узел может присутствовать и молчать.

**Почему это работает через Docker Desktop.** Сессия zenoh поднята в режиме `client`
(`deploy/transport/zenoh_session_config.json5:14`), multicast и gossip выключены, поэтому
контейнер делает ровно одно **исходящее** TCP-соединение на `EDGE_HOST:7447`. Это проходит через
NAT Docker Desktop без `network_mode: host`, которого на Windows и macOS попросту нет.

**Если ничего не подключается** — начните с проверки `router` (см. таблицу в §4):

```bash
# Linux/macOS
nc -vz 192.168.1.10 7447
# Windows PowerShell
Test-NetConnection 192.168.1.10 -Port 7447
```

## 4. Красная проверка — что это значит и что делать

Проверки идут в фиксированном порядке. Блокирующие (красные и «ожидание») не дают перейти к
шагу 5 «Испытание»; совещательные (жёлтые) только предупреждают.

Идентификаторы в первом столбце — те же, что консоль показывает в строке проверки.

| Проверка | Что это значит | Что сделать |
|---|---|---|
| `graph` | Консоль не видит в ROS-графе никого, кроме себя. Транспорт не поднят или домен другой. | Сверьте `ROS_DOMAIN_ID` в `docker/.env` и на роботе. Проверьте `EDGE_HOST`. В докере это профиль `robot` и переменная `ZENOH_CONFIG_OVERRIDE`. |
| `router` | TCP-порт `EDGE_HOST:7447` не отвечает. Роутер zenoh на edge не запущен либо закрыт брандмауэром. | На edge: `systemctl is-active rmw-zenoh-router`, `ss -ltn \| grep 7447`, `sudo ufw allow 7447/tcp`. Если службы нет — шаг 1 из §3. |
| `link` | Часть ключевых потоков молчит или устарела. Пока робот поднимается — это ожидание, а не поломка. | Посмотрите, какие именно потоки названы молчащими, и поднимите соответствующий терминал из шага 3/4. Молчит только камера — проверьте Edge T1. |
| `clock` (только sim) | Gazebo не публикует `/clock`. Весь стек с `use_sim_time:=true` будет стоять: таймеры и TF не тикают. | Проверьте журнал стека: gz мог не стартовать (в контейнере — без GUI) или стоять на паузе. Перезапустите стек. |
| `health` | Сам `/robot_health` не приходит или устарел — консоль просто не знает состояния компонентов. | В симуляции агрегатор поднимает `vlm_sim_bringup` (`start_monitor`), на железе он внутри `hardware_bringup.launch.py`. Если узел жив, а сообщений нет — он завис на пробе. |
| `health:realsense` | Нет свежих кадров камеры. | На Pi — Pi T2. На edge — Edge T1 (реле). |
| `health:scan` | Нет `/scan`. Nav2 без него не поедет. | `/scan` собирается из depth через `depthimage_to_laserscan` на Pi (Pi T1). Проверьте, что depth-поток идёт. |
| `health:ekf_odometry` | Нет `/odometry/filtered`. | На железе — Pi T1 (EKF внутри `hardware_bringup`). **В симуляции красная всегда** — см. примечание под таблицей. |
| `health:wheel_odometry` | Нет `/diff_cont/odom`. | На железе — не загрузился контроллер `diff_cont`, смотрите `controller_manager`. **В симуляции красная всегда** — см. примечание. |
| `health:control_epos4` | Приводы EPOS4 не отвечают по CAN. | `ip -details link show can0`; `sudo ip link set can0 up type can bitrate 1000000`; питание на приводах; терминирование шины. Раздел B чек-листа HIL. **В симуляции зелёная не значит «приводы живы»** — см. примечание. |
| `health:twist_mux` | Нет мультиплексора скоростей — команды до колёс не дойдут. | Pi T1. |
| `health:search_coordinator` | Executive не поднят: некому исполнять skill-и. | Pi T5. |
| `nav2` | Либо узлы Nav2 не видны в графе, либо они **есть, но не `active`**. Присутствие узла ничего не доказывает: он может висеть в `unconfigured`. | Нет узлов — Pi T4 (`navigation_launch.py`). Есть, но не активны — `ros2 lifecycle get /planner_server`; обычно `lifecycle_manager` не дождался карты, `/scan` или TF. |
| `planner:detector` | Нет свежего heartbeat детектора (нужен для `vlm` и `mock`). | Edge T2. Проверьте путь к `venv_python` и наличие весов YOLOE. |
| `planner:orchestrator` | Нет свежего heartbeat оркестратора. `DEGRADED` означает открытый circuit breaker и откат в FLAT. | Edge T3. Для `flat` эта проверка не требуется и не блокирует (`planner:nodes` показывает это явно). |
| `vlm_creds` | Токен, base URL или модель не заданы, либо проверка связи вернула ошибку. | Шаг 3 мастера. Текст ошибки конкретный: 401 — токен неверный или истёк, 404 — base URL должен оканчиваться на `/v1` и не содержать `/chat/completions`. |
| `mission_epoch` | Эпохи миссии разошлись: оркестратор штампует одну, исполнитель ждёт другую. Все его цели будут отклонены как zombie, и внешне это выглядит как «команды уходят, робот стоит». | Перезапустите оркестратор (Edge T3). Это реальная ловушка стека, а не гипотетическая. |
| `world` (только sim) | Выбран мир со статусом `broken` (ошибка) или `limited` (предупреждение). | Возьмите другой мир. Причина написана прямо в карточке (§5). |
| `frontiers` | Совещательная. `frontier_extractor` не найден в графе — фаза SEARCH не получит ни одной цели, и робот будет стоять. | В симуляции его поднимает `flat_sim_bringup` (`start_frontier_extractor:=true`); на железе он по умолчанию выключен. Если узел есть, а робот всё равно стоит — карта пуста: нажмите «Засеять карту (вращение на месте)». |
| `catalog:N` | Совещательная. В `config/worlds.yaml` есть запись, которая не сходится с файлом на диске. | Текст проблемы показывается целиком. Обычно — переименованный `.sdf` или неверный `world_name`. |

**Ловушка симуляции.** `ekf_odometry` и `wheel_odometry` в Gazebo красные **всегда**: EKF в
симуляции не запускается, а мост публикует `/odom` вместо `/odometry/filtered` и
`/diff_cont/odom`. Требовать их означало бы никогда не дать зелёный свет, поэтому в режиме `sim`
они переведены в совещательные и не блокируют старт.

**Обратная ловушка.** `control_epos4` в симуляции зелёная не потому, что приводы живы, а потому
что Gazebo публикует `/joint_states` своим `JointStatePublisher`. Она не доказывает **ничего** про
EPOS4 и CAN. Консоль подписывает это прямо рядом с индикатором.

## 5. Выбор мира и превью (только симуляция)

На шаге 2 мастера показана сетка карточек из `ar_project/config/worlds.yaml`. В карточке —
превью-план этажа, габариты, число комнат и бейдж статуса:

* **ok** — мир пригоден для испытаний. Основной — `house` (квартира из шести комнат, единственный
  мир, поверх которого гоняются сценарии домашнего бенчмарка, см.
  [`HOUSE_BENCHMARK.md`](HOUSE_BENCHMARK.md)). Быстрая проверка детекции — `flat_detect`
  (билборд `bus` в двух метрах перед точкой старта).
* **limited** — мир загрузится, но с оговоркой, и она написана в карточке. У `test_1`…`test_3`
  материалы в синтаксисе Gazebo Classic не резолвятся `gz-sim`, стены будут серыми. У `empty`
  вообще нет стен: фронтиры не замыкаются, для испытаний он непригоден и оставлен как отладочный.
* **broken** — карточка затемнена и не выбирается. `demo1` ссылается на абсолютные пути Fuel вида
  `/home/<user>/.gz/...` и на другой машине не загрузится; `obstacles` и
  `obstacles_with_seg_tests` ссылаются на модель `construction_barrel`, которой нет в
  `ar_project/models`.

Превью — это **SVG-планы, собранные офлайн** парсером SDF: без Gazebo, GPU и внешних библиотек.
Перегенерировать (например, после правки мира):

```bash
ros2 run ar_project make_world_previews.py            # только недостающие
ros2 run ar_project make_world_previews.py --force    # перерисовать все
```

Чтобы добавить свой мир: положите `.sdf` в `ar_project/ar_project/worlds/`, добавьте запись в
`config/worlds.yaml` и прогоните генератор превью. **Поле `world_name` берите ИЗ САМОГО ФАЙЛА**
(`<world name="...">`), а не придумывайте: gz-сервисы адресуются как
`/world/<world_name>/create|set_pose`, и у большинства миров внутри стоит `default`. Ошибка здесь
проявляется не при загрузке мира, а позже — молчащим спавном робота.

## 6. Токен и модель VLM

**Где хранится.** Токен, `VLM_BASE_URL` и `VLM_MODEL` записываются в
`object_tracking/planner_orchestrator/vlm.env` с правами `0600`. Файл в `.gitignore`, владелец —
вы. В контейнер он попадает bind-mount-ом каталога (см. предупреждение в §2).

**Почему консоль его не показывает.** Токен не возвращается в API ни в каком виде: наружу
отдаётся только `token_set: true|false`. Он не пишется в журнал, не попадает в текст ошибок (весь
сетевой и исключенческий текст пропускается через `scrub`) и **не передаётся ROS-параметром** —
`ros2 param get` может прочитать кто угодно в том же домене. Поле ввода на шаге 3 после успешного
сохранения очищается и заменяется на `••••••••`.

**Проверка связи.** Кнопка «Проверить связь» делает два запроса: `GET /models` (он же возвращает
список моделей для выпадающего списка) и один минимальный `chat/completions` с `max_tokens=1`.
Отдельной кнопки «загрузить модели» не нужно — список приходит той же проверкой. Если сервер не
реализует `/models`, впишите имя модели вручную.

**Когда нужен перезапуск.** Оркестратор читает окружение **при старте процесса**. После смены
токена или модели:

* в симуляции — нажмите «Применить и перезапустить», консоль владеет процессом и перезапустит его
  сама;
* на железе — консоль процессом не владеет и честно напечатает команду для edge. До перезапуска
  Edge T3 оркестратор продолжит работать со старыми учётными данными; никакой ошибки при этом не
  будет, просто изменения не применятся.

## 7. Известные ограничения

Читайте этот раздел до того, как делать выводы из прогонов.

**Это «общий верхний слой + два разных нижних», а не единая логика.** Верхний слой действительно
один и тот же: протокол executive (skill-серверы `ExploreFrontier` / `GoToPose` /
`ApproachDetection` / `GetObservation` / `Stop`), детектор, оркестратор, дашборд, протокол миссии.
Нижний слой различается по существу: Gazebo против RealSense + CAN/EPOS4. Формулировка «одна и та
же логика в симуляции и на железе» была бы преувеличением.

**Колея (`wheel_separation`) задана в трёх местах, и они разъехались.**

| Источник | Значение | Якорь |
|---|---|---|
| геометрия URDF (`wheel_offset_y` = 0.1745 → база) | 0.349 м | `description/robot_core.xacro:21` |
| плагин `gz DiffDrive` — одометрия симуляции | 0.295 м | `description/gazebo_control.xacro:8` |
| `diff_drive_controller` на железе | 0.35 м (× 1.0052 = 0.3518 м) | `config/epos4_diffdrive/ros2_controllers.yaml:22,29` |

Следствие: угловая скорость по одометрии считается по **разной** колее, поэтому метрики пути
(длина траектории, число поворотов, накопленный курс) между режимами напрямую **несравнимы**.
Числа оставлены как есть сознательно: железо откалибровано под свои значения
(`wheel_separation_multiplier = 1.0052`), и правка любого из них означает перекалибровку стенда.
Проверка `ar_project/test/check_urdf_parity.py` печатает это расхождение при каждом запуске.

**Перцепция не идентична.** В симуляции `horizontal_fov` задан литералом `1.089` рад
(`description/camera_gazebo_sensors.xacro:19,61`) и каноном не управляется. На железе intrinsics
приходят из `camera_info` RealSense. Совпадают только ширина, высота, частота и дальности отсечения
— их и сверяет `check_urdf_parity.py` с `fleet_comms.mode_profiles.urdf_canon()`. Кроме того,
дефолт симуляции — 320×240 (640×480 роняет RTF в WSL2 и рвёт синхронизацию RTAB-Map с одометрией);
режим «сопоставимо с железом» 640×480 включается сознательно и стоит скорости.

**На macOS режим `vlm` практически недоступен.** YOLOE на CPU для кадра 640×480 непригоден по
времени. На Apple Silicon реально работают только `planner=flat` и `planner=mock`.

**`gui:=true` внутри контейнера не работает** — в контейнере нет `DISPLAY`. Gazebo поднимается
headless, и включать GUI в docker-режиме бессмысленно. Для GUI поднимайте стек без Docker в WSL
или на Linux-хосте; `./run.sh native` печатает нужные команды.

**`tune_camera_compression.sh` нельзя выполнить до подъёма edge-реле.** Параметры
`compressedDepth.*` объявляются лениво, только когда появится подписчик. Это отдельный шаг
**после** шага 4, а не часть подъёма Pi.

**Межхостовой zenoh Pi↔edge в репозитории ещё не валидирован.** Проверено только на одном хосте в
WSL: конфигурации загружаются, роутер стартует, доставка идёт через роутер без multicast
(`deploy/transport/README.md:63-65`). Измеренный межхостовой джиттер в пределах бюджетов 0.2 с
(TF) / 0.35 с (depth-match) / 1.5 с (возраст пикселей) — открытый пункт, он закрывается разделами
C и D чек-листа [`HIL_BRINGUP_CHECKLIST.md`](HIL_BRINGUP_CHECKLIST.md).

**Профиль «детектор и оркестратор на вашем ПК против реального робота» не предусмотрен
намеренно.** Он нарушил бы инвариант единственного потребителя камеры: сейчас поток Pi забирает
ровно один узел — реле на edge, а все остальные читают локальные `/camera_edge/*`. Второй прямой
подписчик на `/camera/camera/*` заново открывает поток по Wi-Fi и кладёт канал. Поэтому «мозг»
живёт либо целиком на edge, либо целиком в симуляции.

**Журнал не переживает падение контейнера.** Журнал запуска стека и лента событий миссии — это
кольцевые буферы в памяти процесса консоли. При перезапуске контейнера они пусты. Если прогон
нужен для отчёта, сохраняйте вывод терминалов на Pi и edge отдельно.

**Профили `console` и `edge`/`all` несовместимы.** Консоль сама порождает верхний слой, а профили
`edge`/`all` поднимают вторые экземпляры детектора и оркестратора. `run.sh`/`run.ps1` проверяют это
и останавливаются с объяснением.

## 8. Ввод задания и «Стоп»

Для режима **VLM** нужен **чистый лейбл** объекта: `chair`, `bus`, `person`. Не `find a chair` и
не «найди стул»: лейбл уходит в детектор как текстовый промпт открытого словаря, и глагол в нём
ухудшает детекцию. Для режима **FLAT** можно вводить фразу — она нормализуется `PromptBridge`.

Кнопка **«Стоп»** делает две вещи одновременно: отправляет `Stop`-action (`SOFT_STOP`, помечен как
epoch-exempt, поэтому доходит и при разъехавшихся эпохах) и публикует `/vlm_mission/cancel`.
Первое гарантированно останавливает **движение**; второе прекращает цикл VLM-миссии на ближайшей
границе шага, публикует `mission_end` с причиной `cancelled` и вызывает skill `Stop`. Это
операторский abort, а не ограничение планировщика.

Повторная отправка задания во время идущей миссии **не** теряется молча: консоль вернёт ошибку с
номером текущего шага и предложит сначала нажать «Стоп».

## 9. Проверка детерминизма URDF

```bash
python3 ar_project/ar_project/test/check_urdf_parity.py            # канон симуляции 320x240
python3 ar_project/ar_project/test/check_urdf_parity.py --hw-parity  # канон 640x480
```

Это инструмент разработчика, а не установленная нода. Он:

* сравнивает поддеревья `link`/`joint` симуляционного и железного URDF **без** `<gazebo>` и
  `<ros2_control>` — эти два блока и есть «разные нижние слои», а всё остальное обязано совпасть
  до шестого знака (абсолютные пути от `$(find ar_project)` при этом нормализуются, иначе тексты
  никогда не совпадут на двух разных машинах);
* отдельно достаёт из симуляционного URDF `<gazebo>/<sensor>/<camera>` и сверяет `width`,
  `height`, `update_rate` и дальности отсечения с активным каноном из `fleet_comms.mode_profiles`;
* печатает расхождение колеи по трём источникам (таблица в §7);
* проверяет, что в железный URDF не просочился симуляционный плагин `gz_ros2_control`.

Коды возврата: `0` — паритет, `1` — расхождение, `2` — ошибка рендера xacro, `77` — пропуск
(`xacro` в системе нет).
