# Исследовательский отчет по SLAM, сенсорному слиянию и архитектуре поиска объекта

## 1. Назначение системы

В проекте реализована мобильная робототехническая система, способная строить карту помещения, локализоваться относительно нее, принимать текстовый запрос на объект и автономно подъезжать к найденному объекту. Система объединяет три контура:

- контур одометрии и SLAM;
- контур визуального поиска объекта;
- контур преобразования результата CV в навигационную цель для Nav2.

Архитектура разделена между двумя вычислительными устройствами. Raspberry Pi 5 выполняет задачи реального времени: работа с колесной базой, камера, EKF, RTAB-Map, Nav2 и преобразование точки объекта в навигационную цель. Ноутбук выполняет тяжелый CV-инференс, так как модели сегментации и grounding требуют GPU.

## 2. Используемые сенсоры

### 2.1 Колесные энкодеры

Колесная база управляется через `diff_drive_controller`. Контроллер получает обратную связь по положению колес и публикует сырую колесную одометрию `/diff_cont/odom`.

Текущие физические параметры базы:

- `wheel_separation: 0.354 м`;
- `wheel_radius: 0.0385 м`;
- `publish_rate: 50 Hz`;
- `position_feedback: true`;
- `open_loop: false`;
- `velocity_rolling_window_size: 20`.

Калибровочные множители радиуса и базы в текущей основной реализации не используются. Это сделано для того, чтобы не смешивать физическую геометрию платформы с эмпирической подстройкой под отдельные тестовые команды. Шум колесной одометрии сглаживается за счет rolling-window фильтрации скоростей в контроллере и последующего EKF.

Сырая колесная одометрия не публикует авторитетный TF `odom -> base_link`, потому что в контроллере задано:

```yaml
enable_odom_tf: false
```

Авторитетная трансформация `odom -> base_link` публикуется EKF.

### 2.2 IMU камеры RealSense D435i

RealSense D435i предоставляет гироскоп и акселерометр. В launch-файле камеры включены:

- `enable_gyro: true`;
- `enable_accel: true`;
- `unite_imu_method: 2`.

В основной конфигурации EKF используется сырой IMU-топик `/camera/camera/imu`, но не используется абсолютная ориентация IMU. В фильтр передается только `angular_velocity.z`, то есть угловая скорость вокруг вертикальной оси.

Ранее проверялся вариант с `imu_filter_madgwick` и топиком `/camera/camera/imu/data`, где в EKF подавался yaw. Этот подход оказался недостаточно устойчивым: при неподвижном роботе ориентация IMU медленно дрейфовала. Поэтому текущий основной режим отключает ориентационный фильтр IMU и использует гироскоп только как источник угловой скорости.

### 2.3 RGB-D камера

Камера RealSense используется в двух ролях:

- RGB-D источник для RTAB-Map;
- RGB-D источник для CV-пайплайна поиска объектов.

Текущие профили камеры:

- RGB: `640x480x15`;
- depth: `424x240x15`;
- `enable_sync: true`;
- `align_depth.enable: true`;
- `pointcloud.enable: false`.

Глубина выравнивается к цветному изображению. Публикация point cloud отключена по умолчанию, чтобы не перегружать Raspberry Pi.

## 3. Слияние данных одометрии

Слияние данных выполняется пакетом `robot_localization` через EKF. Основная схема:

```text
/diff_cont/odom
    -> EKF

/camera/camera/imu
    -> EKF

EKF
    -> /odometry/filtered
    -> TF odom -> base_link
```

EKF работает в 2D-режиме:

```yaml
two_d_mode: true
frequency: 20.0
world_frame: odom
```

Из колесной одометрии в текущей конфигурации используются:

- `yaw`;
- `vx`;
- `vyaw`.

Из сырого IMU используется:

- `angular_velocity.z`.

Позиции `x/y` из колесной одометрии напрямую в EKF не подаются. Это снижает риск дублирования информации, поскольку pose и twist в `/diff_cont/odom` вычисляются из одного и того же источника - энкодеров. При этом `vx` остается основным источником поступательного движения, а yaw и yaw-rate помогают удерживать ориентацию робота в условиях бедной визуальной сцены.

Дополнительно в конфиге предусмотрен опциональный источник `/visual_odom`, от которого можно брать только `x/y` как мягкую коррекцию. В основной дипломной конфигурации визуальная одометрия не используется, так как сцена может быть визуально бедной и визуальная регистрация может срываться.

## 4. RTAB-Map и построение карты

RTAB-Map работает на Raspberry Pi вместе с Nav2. Это важно для устойчивости навигации: SLAM и Nav2 используют одну и ту же локальную временную базу, TF-граф и карту, без задержек между машинами.

RTAB-Map получает:

- RGB: `/camera/camera/color/image_raw`;
- aligned depth: `/camera/camera/aligned_depth_to_color/image_raw`;
- camera info: `/camera/camera/color/camera_info`;
- odometry: `/odometry/filtered`.

Ключевые параметры:

- `rgbd_sync: true`;
- `approx_sync: true`;
- `approx_sync_max_interval: 0.2`;
- `topic_queue_size: 60`;
- `sync_queue_size: 60`;
- `visual_odometry: false`;
- `icp_odometry: false`;
- `publish_tf_odom: false`;
- `publish_tf_map: true`.

RTAB-Map публикует трансформацию `map -> odom`. EKF публикует `odom -> base_link`. Итого полный путь положения робота в карте:

```text
map -> odom -> base_link
```

Важно, что RTAB-Map не исправляет саму `/odometry/filtered`. Он корректирует положение робота в глобальной карте через `map -> odom`. Поэтому при слабых loop closure или бедной визуальной сцене накопленная ошибка колесной одометрии может проявляться как смещение карты или положения робота в RViz.

Карта строится по RGB-D данным. По умолчанию debug point cloud отключен, а препятствия формируются на стороне RTAB-Map через occupancy grid:

- `Grid/3D false`;
- `Grid/RayTracing true`;
- `Grid/RangeMax 3`;
- `Grid/MaxGroundHeight 0.05`;
- `Grid/MaxObstacleHeight 0.4`.

В базовом launch-файле `detection_rate` равен `2 Hz`, но в экспериментах можно увеличивать его, например до `5 Hz`, если Raspberry Pi выдерживает нагрузку.

## 5. Nav2 и использование карты

Nav2 работает на Raspberry Pi и использует:

- карту из RTAB-Map;
- TF `map -> odom -> base_link`;
- одометрию `/odometry/filtered`;
- цели `/goal_pose`.

В `navigation_launch.py` Nav2 controller публикует команды в `cmd_vel_nav`, затем `velocity_smoother` сглаживает их в `/cmd_vel`. Далее команды проходят через `twist_mux` и преобразуются в `TwistStamped` для `/diff_cont/cmd_vel`.

Текущие ограничения скорости:

- `max_vel_x: 0.5 м/с`;
- `max_vel_theta: 1.57 рад/с`;
- `xy_goal_tolerance: 0.10 м`;
- `yaw_goal_tolerance: 0.15 рад`.

Навигация к объекту начинается после того, как модуль `target_pixel_to_goal` опубликует `/goal_pose`.

## 6. Распределение вычислений между Raspberry Pi и ноутбуком

Raspberry Pi выполняет:

- запуск RealSense;
- колесную базу и `diff_drive_controller`;
- EKF `/odometry/filtered`;
- RTAB-Map;
- Nav2;
- передачу RGB-D данных на ноутбук;
- преобразование результата CV в `/goal_pose`.

Ноутбук выполняет:

- получение сжатого RGB и depth-потока от Raspberry Pi;
- запуск CV-моделей;
- сегментацию/grounding объекта по текстовому prompt;
- выбор опорной точки объекта;
- публикацию `/target_pixel` обратно на Raspberry Pi.

Такое разделение снижает нагрузку на Raspberry Pi и позволяет использовать GPU ноутбука для тяжелых моделей.

## 7. Передача RGB-D данных на ноутбук

Передача выполняется узлом `tracker_rgbd_bridge.py`, который запускается на Raspberry Pi.

Входные топики:

- `/camera/camera/color/image_raw`;
- `/camera/camera/aligned_depth_to_color/image_raw`.

Выходные топики для ноутбука:

- `/tracker/color/image_raw/compressed`;
- `/tracker/aligned_depth_to_color/image_raw`.

RGB кадр сжимается в JPEG:

- `jpeg_quality: 90`.

Depth передается как raw `sensor_msgs/Image`, но не весь поток, а только синхронизированные пары с ограниченной частотой.

По умолчанию:

- `max_publish_rate: 1.0 Hz`;
- `sync_tolerance: 0.15 s`.

Узел хранит последние RGB и depth кадры, выбирает свежий RGB, ищет ближайший depth по timestamp и публикует пару только если разница timestamp меньше `sync_tolerance`. Передача включается только после получения prompt на `/target_prompt` и выключается после публикации goal lock на `/target_goal_locked`.

Такой режим нужен, чтобы не забивать Wi-Fi полным RGB-D потоком `15 FPS`. Вместо этого на ноутбук передаются только кадры, полезные для активного поиска объекта.

## 8. Отправка prompt и запуск поиска

Пользователь отправляет запрос на объект через `/target_prompt_request`. Узел `reliable_prompt_sender.py` публикует его в `/target_prompt` и ждет подтверждения от Raspberry Pi на `/target_prompt_ack`.

Параметры надежной доставки:

- `retry_period: 0.5 s`;
- `max_retries: 12`.

После получения prompt Raspberry Pi делает несколько действий:

- `target_pixel_to_goal` сбрасывает старую цель, очищает историю стабильности и публикует ack;
- `tracker_rgbd_bridge` включает экспорт RGB-D пар на ноутбук;
- CV-нода на ноутбуке активирует tracking для нового prompt.

Повторные одинаковые prompt во время активного прогона игнорируются, чтобы надежная доставка не создавала дубликаты trial и не сбрасывала состояние поиска.

## 9. CV-пайплайн поиска объекта

На ноутбуке используется `sam_node_continuous.launch.py`, который запускает `rgb_tracker_node.py` в continuous-режиме.

Поддерживаемые режимы модели:

- `dino_mobilesam`: GroundingDINO + MobileSAM;
- `clip`: CLIPSeg;
- `yoloe`: YOLOE;
- `florence2`: Florence-2 в режиме referring expression segmentation.

Основные параметры continuous-режима:

- вход RGB: `/tracker/color/image_raw/compressed`;
- вход depth: `/tracker/aligned_depth_to_color/image_raw`;
- `use_depth_input: true`;
- `depth_match_tolerance: 0.2 s`;
- `target_publish_rate: 3.0 Hz`;
- `continuous_frame_max_age: 2.0 s`;
- `continuous_rgb_stamp_max_age: 1.0 s` в launch-файле;
- `publish_mask_in_continuous: false`;
- min mask area для моделей: `100 px`.

CV-нода не обязана обрабатывать каждый пришедший кадр. В continuous-режиме она хранит последний полученный кадр. Когда модель освобождается после инференса, она берет самый свежий доступный кадр, а старые кадры отбрасываются. Это предотвращает накопление очереди и уменьшает задержку управления.

После сегментации объект представлен маской и центральной точкой. Однако для навигации по объектам с вытянутой геометрией центр маски может быть плохой целью. Например, у стула центр маски может попадать в дальнюю ножку. Поэтому в continuous-режиме используется depth-aware выбор точки:

1. Модель строит маску объекта.
2. Depth кадр сопоставляется с RGB по timestamp.
3. На маске выбираются только валидные depth-пиксели.
4. Находится не одиночный минимальный depth-пиксель, а устойчивый ближний depth-уровень по нижнему перцентилю глубины.
5. Берется не весь объект, а ближайшая к камере область в полосе `nearest_depth + nearest_depth_band_m`.
6. Если в ближайшей области слишком мало согласованных depth-пикселей, обновление цели отбрасывается как ненадежное.
7. Из этой области выбирается пиксель, ближайший к anchor-точке.

Таким образом `/target_pixel` в continuous-режиме содержит не просто центр маски, а ближайшую валидную по depth точку на маске. Глубина этой точки записывается в `point.z`, поэтому Raspberry Pi не обязана заново сопоставлять mask и depth.

Дополнительно на стороне Raspberry Pi реализована защитная проверка embedded depth. Если ноутбук прислал точку с глубиной, но локальная depth-карта Raspberry Pi в небольшой окрестности этого пикселя видит существенно более близкую поверхность, используется локальная ближняя depth-точка. Это защищает систему от случаев с тонкими объектами, например стульями с тонкими ножками, когда выбранная CV-точка может попасть в фон за объектом.

У этого режима есть важное ограничение. Он полезен, когда целевой объект сам является тонким или плохо измеряемым depth-камерой, но может быть вреден для дальних объектов, перед которыми в сцене находится ближнее препятствие. Например, если коробка хорошо видна далеко за стулом или столом, ноутбук может корректно выбрать точку коробки с depth около `4 м`, а Raspberry Pi в локальной окрестности того же пикселя может найти более близкую поверхность около `3.4 м` и заменить embedded depth на нее. В этом случае навигационная цель будет построена не по коробке, а по ближнему препятствию или поверхности перед ней. В логах такая ситуация видна по строке:

```text
Embedded target depth guarded by local depth:
pixel=(u0, v0) -> (u1, v1), embedded_depth=4.09m, local_depth=3.42m.
```

Таким образом, Pi-side depth guard является компромиссным режимом. Для стульев, тонких ножек и объектов с дырками в depth он повышает безопасность, не позволяя выбрать фон за объектом. Для дальних объектов за частичным foreground-препятствием он может преждевременно "притянуть" цель к ближней поверхности. Поэтому режим должен рассматриваться как настраиваемая защита, а не универсальное правило. Для сцен с дальними целями за препятствиями его можно отключать аргументом:

```bash
embedded_depth_guard_radius_px:=0
```

В continuous-режиме маска по умолчанию не передается обратно на Raspberry Pi:

```yaml
publish_mask_in_continuous: false
```

Это снижает нагрузку на сеть. На Raspberry Pi отправляется компактный результат:

```text
/target_pixel:
    x = u пикселя
    y = v пикселя
    z = depth_m выбранной точки
```

## 10. Преобразование target pixel в навигационную цель

На Raspberry Pi работает узел `target_pixel_to_goal.py`. Он принимает `/target_pixel` от ноутбука и строит 3D-точку объекта в карте.

Основные входы:

- `/target_pixel`;
- `/camera/camera/color/camera_info`;
- `/camera/camera/aligned_depth_to_color/image_raw`;
- TF `map -> odom -> base_link`;
- `/navigate_to_pose/_action/status`.

Если `/target_pixel.point.z` содержит валидную depth, используется embedded depth с ноутбука. Если depth не встроена, узел ищет локальный depth кадр на Raspberry Pi и может использовать `/target_mask` как fallback.

Алгоритм:

1. Проверяется возраст сообщения `/target_pixel`.
2. Проверяется стабильность серии детекций.
3. Пиксель `(u, v)` и depth преобразуются в 3D-точку в frame камеры.
4. Через TF точка переводится в `map`.
5. Считается направление от текущего положения робота к объекту.
6. Публикуется цель не в сам объект, а на расстоянии `approach_offset` от него.

Текущий stop-offset:

```yaml
approach_offset: 0.58
```

Это расстояние считается от `base_link` до выбранной 3D-точки объекта. Поскольку передняя часть корпуса находится впереди `base_link`, отдельно для метрик используется:

```yaml
front_robot_x: 0.275
```

## 11. Устойчивость цели

Стабильность цели реализована несколькими независимыми фильтрами.

### 11.1 Фильтр возраста target pixel

Если `/target_pixel` слишком старый, он отбрасывается:

```yaml
max_target_pixel_age_s: 1.5
```

Это защищает систему от ситуации, когда модель обработала старый кадр, а робот уже успел заметно переместиться.

### 11.2 Требование стабильных детекций

Перед публикацией цели узел требует несколько согласованных детекций:

```yaml
required_stable_detections: 2
stable_pixel_tolerance: 25 px
embedded_stable_pixel_tolerance: 90 px
```

Если новый target pixel резко отличается от предыдущего, окно стабильности сбрасывается. Это снижает риск публикации цели по случайной ложной детекции.

### 11.3 Ограничение минимального обновления цели

Чтобы не публиковать слишком мелкие изменения, используется:

```yaml
min_goal_update_distance: 0.15 м
min_goal_update_angle: 0.2 рад
```

Если новая цель почти совпадает с предыдущей, она не публикуется повторно.

### 11.4 Запрет резких скачков цели

После начала движения новые цели фильтруются по максимальному скачку:

```yaml
max_goal_update_distance: 0.50 м
max_goal_update_angle: 0.70 рад
```

Если CV внезапно перескочила на другой объект или другую часть сцены, такая цель отклоняется. Это особенно важно в сценах, где похожие объекты находятся рядом или где сегментация может перескочить с целевого объекта на мебель рядом.

### 11.5 Заморозка финального подхода

В continuous-режиме цель может уточняться во время движения. Однако вблизи объекта новые обновления становятся опасными: из-за перспективы, частичного выхода объекта из кадра или задержки CV цель может начать прыгать.

Поэтому введена зона финального подхода:

```yaml
final_approach_freeze_distance: 0.80 м
```

Когда наблюдаемая дистанция до объекта становится меньше или равна этому порогу, `target_pixel_to_goal` публикует `/target_goal_locked = true`. После этого:

- новые target updates игнорируются;
- `tracker_rgbd_bridge` прекращает передачу RGB-D кадров на ноутбук;
- CV-нода останавливает tracking до нового prompt;
- робот завершает движение к последней принятой цели "вслепую".

Этот механизм нужен для устойчивого завершения подъезда, особенно при повышенной скорости робота.

## 12. Поведение при потере объекта

Если CV во время движения перестает находить объект, новая цель не публикуется. Nav2 продолжает движение к последней валидной цели. Это желательное поведение для случаев, когда объект частично выходит из кадра на финальном участке: робот не должен аварийно сбрасывать навигацию только потому, что объект перестал быть виден в текущем RGB кадре.

Если цель уже была опубликована, потеря объекта влияет только на дальнейшие уточнения, но не отменяет текущий Nav2 goal.

## 13. Завершение прогона и метрики

Когда Nav2 сообщает `Goal succeeded`, `target_pixel_to_goal` блокирует дальнейшие обновления цели и публикует `/target_goal_locked = true`.

Дополнительно после прибытия считается автоматическая оценка расстояния до ближайшего объекта перед роботом:

```text
/experiment/fd_auto
```

Она вычисляется по последнему depth кадру с учетом положения передней точки корпуса:

- `front_robot_x: 0.275`;
- `fd_distance_mode: forward`;
- `fd_lateral_limit_m: 0.60`;
- `fd_nearest_depth_band_m: 0.03`.

Экспериментальный логгер записывает:

- prompt;
- модель CV;
- время CV;
- задержку до первой цели;
- длительность прогона;
- итоговый статус Nav2;
- `fd_auto_m`.

Повторные одинаковые prompt не создают новые trial, чтобы надежная доставка prompt не засоряла CSV строками `superseded`.

## 14. Итоговая архитектура одного прогона

Полная последовательность:

```text
1. Пользователь отправляет prompt в /target_prompt_request.
2. reliable_prompt_sender публикует /target_prompt до получения /target_prompt_ack.
3. Raspberry Pi принимает prompt:
   - сбрасывает старую цель;
   - снимает goal lock;
   - подтверждает prompt.
4. tracker_rgbd_bridge включает передачу RGB-D пар на ноутбук.
5. Ноутбук получает compressed RGB + raw depth.
6. CV-модель сегментирует объект по текстовому prompt.
7. На маске выбирается ближайшая валидная depth-точка.
8. Ноутбук публикует /target_pixel с embedded depth.
9. Raspberry Pi преобразует пиксель в 3D-точку в map.
10. target_pixel_to_goal фильтрует цель по возрасту, стабильности и скачкам.
11. Публикуется /goal_pose для Nav2.
12. Nav2 строит путь и управляет базой.
13. Пока робот далеко от объекта, цель может уточняться.
14. При входе в final_approach_freeze_distance цель замораживается.
15. Передача RGB-D и CV tracking останавливаются.
16. Робот завершает движение к последней принятой цели.
17. После успеха Nav2 публикуется fd_auto_m и логгер закрывает trial.
```

## 15. Ключевые проектные решения

1. SLAM и Nav2 размещены на Raspberry Pi, чтобы исключить рассинхронизацию навигации и карты между машинами.
2. Тяжелые CV-модели вынесены на ноутбук с GPU.
3. На ноутбук передается не полный поток камеры, а ограниченные по частоте RGB-D пары.
4. RGB сжимается в JPEG, depth передается только в составе синхронизированных пар.
5. В continuous-режиме CV обрабатывает самый свежий доступный кадр, а не очередь старых кадров.
6. Для навигации используется ближайшая depth-точка на маске, а не центр маски.
7. Raspberry Pi получает компактный `/target_pixel` с embedded depth, а не тяжелую маску.
8. Цель фильтруется по возрасту, стабильности и допустимому скачку.
9. Вблизи объекта цель замораживается, чтобы робот не реагировал на нестабильные поздние обновления.
10. Потеря объекта после публикации цели не отменяет движение: робот завершает подъезд к последней надежной цели.

## 16. Ограничения текущей реализации

Основные ограничения связаны с качеством одометрии, бедностью визуальной сцены и задержкой CV-инференса. RTAB-Map корректирует положение через `map -> odom`, но не исправляет саму `/odometry/filtered`. Если сцена содержит мало устойчивых визуальных признаков или loop closure срабатывает редко, ошибка колесной одометрии может проявляться как накопление смещения карты.

CV-контур зависит от качества текстового prompt и способности выбранной модели отличать похожие объекты. В сложных семантических сценах, например при наличии похожих шкафов и тумб, возможна путаница между объектами. Для таких случаев особенно важны стабильность target updates, ограничение скачков цели и отдельная разметка экспериментов как "сложная семантическая сцена".

Отдельное ограничение связано с Pi-side depth guard для embedded depth. Этот механизм защищает от выбора фона за тонким объектом, но в сценах с дальней целью и ближним препятствием может заменить корректную дальнюю depth-точку на более близкую поверхность. Поэтому результаты таких прогонов нужно интерпретировать с учетом логов `Embedded target depth guarded by local depth`, а сам режим при необходимости отключать для дальних объектов.

Система уже содержит базовые механизмы устойчивости к задержкам и потере объекта, но для динамических препятствий требуется дальнейшее развитие Nav2 costmap: более быстрый obstacle layer, локальные сенсоры препятствий и отдельная логика остановки/перепланирования при внезапном появлении человека или предмета на пути.
