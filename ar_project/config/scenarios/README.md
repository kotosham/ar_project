# Сценарии домашнего бенчмарка

Каталог описывает эпизоды для `house_sim.launch.py` / `house_scenario_runner.py`.
Один эпизод = **сценарий × оверлей помех × планировщик × seed**.

Полное описание бенчмарка, метрик и порядка запуска — [`docs/HOUSE_BENCHMARK.md`](../../../docs/HOUSE_BENCHMARK.md).

## Матрица

7 сценариев × 8 оверлеев = **56 комбинаций** из 15 файлов. Любой сценарий
работает с любым оверлеем: пересечений реквизита нет (проверено покоординатно,
см. комментарии в `p_clutter.yaml`).

| id | что диагностирует | mission | старт робота |
|---|---|---|---|
| `s1_far_target` | подход к цели без данных глубины; декомпозиция большого шага | `chair` | (-7.00, 0.00, 0°) |
| `s2_occlusion` | смена ракурса ради grounding'а | `bottle` | (0.50, -0.30, 0°) |
| `s3_behind` | активный поиск, поворот до поездки | `sports ball` | (1.00, 0.00, 0°) |
| `s4_text_hint` | OCR текстовой подсказки → маршрут | `cup` | (-7.00, 0.00, 0°) |
| `s5_arrow_signs` | символьная разметка + устойчивость к дистрактору | `towel` | (-7.00, 0.00, 0°) |
| `s6_toilet_implies_bathroom` | вывод «объект → помещение» | `bathroom` | (3.20, 0.00, 180°) |
| `s7_neighbor_room` | смежность комнат, выход до поиска | `bathroom` | (5.60, 3.00, 180°) |

Отдельно, вне матрицы: `ctl_reachable` — **положительный контроль** (стул в 4.6 м
прямо по курсу, ни одной из семи трудностей). Прогоняйте его с `planner:=mock`
ПЕРЕД каждым свипом: mock обязан давать `success` / 1.000. Если контроль падает —
сломан стенд (см. шапку файла: реальный пойманный кейс — недобитый
`coordinator_node` и два action-сервера), и интерпретировать нули семёрки нельзя.

| оверлей | что моделирует | `timeout_scale` |
|---|---|---|
| `p_none` | контроль | 1.0 |
| `p_dark_room` | погашен свет в ванной / кухне / гостиной + усиление матрицы | 1.3 |
| `p_dirty_lens` | грязь на объективе: локальная потеря высоких частот | 1.3 |
| `p_carpet` | ковры поперёк коридора: порог 2 см + µ 1.6 | 1.4 |
| `p_puddle` | лужи: µ 0.02, проскальзывание колёс | 1.4 |
| `p_clutter` | коробки, сужающие проход и засоряющие DETECT_ALL | 1.3 |
| `p_dropout` | потеря 25 % кадров + смаз при вращении | 1.3 |
| `p_hard` | темнота + грязь + лужи одновременно | 1.8 |

## Схема сценария

```yaml
id: str                 # обязан совпадать с именем файла без расширения
title: str
description: str
mission: str            # публикуется в /vlm_mission (std_msgs/String)
robot_start: {x: float, y: float, yaw: float}
spawn:                  # реквизит, создаётся через /world/house/create
  - {model: str, name: str, x: float, y: float, z: float, yaw: float}
lights_off: [str]       # имена источников из worlds/house.sdf
subgoals: [...]         # УПОРЯДОЧЕННЫЙ список (см. ниже)
success: {type: all_subgoals}      # либо {type: subgoal, id: <id>}
timeout_s: float
max_path_m: float       # мягкий бюджет пути; превышение логируется, не обрывает
diagnoses: [str]        # теги для агрегации в отчёте
```

`model` и `name` обязательны, `x`/`y` обязательны, `z`/`yaw` по умолчанию 0.
`name` должен быть уникален внутри сценария — Gazebo не создаст две сущности с
одинаковым именем. Реквизит оверлея раннер автоматически переименовывает с
префиксом `p_`, поэтому коллизия имён сценария и оверлея невозможна.

## Схема оверлея

```yaml
id: str                 # обязан совпадать с запрошенным perturbation
title: str
lights_off: [str]       # объединяется (union) со списком сценария
spawn: [...]            # добавляется к реквизиту сценария
camera:                 # профиль для ноды sim_perturbations, шлётся целиком
  smudge: 0.0..1.0
  blur_sigma: float
  darkness: 0.0..1.0    # множитель яркости, 1.0 = без изменений
  noise_sigma: 0.0..255
  dropout_prob: 0.0..1.0
  motion_blur_px: int
timeout_scale: float    # умножает timeout_s сценария
```

Ключи внутри `camera` жёстко фиксированы: неизвестный ключ — ошибка авторинга,
раннер падает с `SetupError`, а не молча игнорирует опечатку.

## Предикаты subgoal'ов

Проверяются на каждом тике (5 Гц) **по порядку**: subgoal засчитывается только
после того, как выполнены все предыдущие. Отсюда `ordered_progress` — длина
самого длинного выполненного префикса, делённая на число subgoal'ов.

| `type` | обязательные ключи | семантика |
|---|---|---|
| `near_xy` | `x`, `y`, `radius` | центр робота в круге радиуса `radius` |
| `in_room` | `room` | центр робота внутри AABB комнаты |
| `saw_label` | `label` (+ `min_conf`) | метка встретилась в событии `detect_all` на `/vlm/activity` |
| `faced_xy` | `x`, `y`, `tol_rad` | курс робота направлен на точку с допуском |
| `mission_done` | — | получено событие `mission_end` |

`saw_label` сравнивает без учёта регистра и принимает вхождение подстроки:
открытый словарь произносит метки свободно («a sports ball»), и требовать
точного равенства значило бы мерить формулировку детектора, а не факт находки.

## AABB комнат

Единственный источник истины — они продублированы в `ROOMS` внутри
`scripts/house_scenario_runner.py` и в `worlds/house.sdf`. Расхождение молча
переоценивает каждый когда-либо посчитанный эпизод.

| комната | x | y |
|---|---|---|
| `hallway` | −7.40 … 7.40 | −1.10 … 1.10 |
| `bedroom` | −7.40 … −2.00 | 1.10 … 4.90 |
| `bathroom` | −2.00 … 2.00 | 1.10 … 4.90 |
| `kitchen` | 2.00 … 7.40 | 1.10 … 4.90 |
| `storage` | −7.40 … −2.00 | −4.90 … −1.10 |
| `living` | −2.00 … 7.40 | −4.90 … −1.10 |

Дверные проёмы: северная стена `y = 1.1` — спальня `x ∈ [−4.60, −3.50]`,
ванная `x ∈ [−0.55, 0.55]`, кухня `x ∈ [3.60, 4.70]`; южная стена `y = −1.1` —
кладовая `x ∈ [−4.60, −3.50]`, гостиная `x ∈ [2.40, 3.50]`.

## Источники света

`light_hallway_w` (−4.50, 0), `light_hallway_c` (0, 0), `light_hallway_e` (4.00, 0),
`light_bedroom` (−4.70, 3.00), `light_bathroom` (0, 3.00), `light_kitchen` (4.70, 3.00),
`light_storage` (−4.70, −3.00), `light_living` (2.70, −3.00) — все на `z = 2.0`,
diffuse 0.62, attenuation range 12 / constant 0.80 / linear 0.05 / quadratic 0.005.
Эти же числа продублированы в `LIGHT_*` раннера: `light_config` заменяет конфигурацию
источника целиком, поэтому расхождение приведёт не к гашению, а к телепортации света.

В `house.sdf` намеренно нет солнца и нет потолка: освещение держится
исключительно на этих точечных источниках, поэтому `light_config` действительно
гасит комнату. Позиции продублированы в `LIGHT_POSES` раннера, потому что
`light_config` заменяет конфигурацию целиком — при несовпадении позы источник не
погаснет, а телепортируется.

## Реквизит

Модели лежат в `../../models/`. Сценарии ссылаются на них по имени каталога
(`model://<name>`).

`target_cup`, `target_bottle`, `target_ball`, `target_towel`, `target_chair`,
`occluder_screen`, `clutter_pile`, `floor_carpet`, `floor_puddle`,
`sign_cup_kitchen`, `sign_arrow_up`, `sign_arrow_right`, `sign_arrow_left`.

`sign_arrow_left` («ВАННАЯ ←») не используется ни одним поставляемым сценарием и
оставлен как заготовка для пользовательских вариантов, где ванная находится
слева по кадру.

### Почему щиты стоят перпендикулярно стене

Камера робота на высоте **0.13 м**, полуугол обзора 31.2°. Перебрано три
варианта монтажа, все проверены живым рендером:

| вариант | что вышло |
|---|---|
| плашмя на стене (`yaw 0`) | щит под 90° к движению — робот не видит его вообще |
| под наклоном −25° | дальний край уходит на пеленг 35°, край кадра срезает пол-щита; чтобы влез целиком, надо отъехать так далеко, что текст нечитаем |
| **перпендикулярно, лицом на запад (`yaw −1.5708`)** | робот подъезжает почти по нормали: ракурс ~19° вместо 44°, щит виден на 93 % ширины вместо 72 % |

Принят третий — «флаг», как в настоящих коридорах. Побочная выгода: габарит щита
по `x` равен его толщине (5 см), поэтому он физически не может перекрыть дверной
проём, и ограничение на расстановку снимается.

Размер полотна — **1.00 × 0.56 м**, центр `y = 0.54`: щит занимает `y` 0.04…1.04,
выступая в коридор на 1.0 м и оставляя 1.08 м прохода южнее. Путевые точки в
`s4`/`s5` заданы на `y = −0.45` — по свободной полосе.

Чтобы полотно попало в кадр целиком, нужно ~2.8 м продольного разгона. Робот
стартует в 2.4 м от западной стены, поэтому щит западнее проёма спальни
прочитать нельзя в принципе — он минуется раньше, чем входит в кадр. Отсюда в
`s5` два щита, а не три.
